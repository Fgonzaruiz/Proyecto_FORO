4. Auditoría de seguridad OWASP-lite

4.1 Hallazgos críticos y altos

  • P0 — Errores PHP visibles en producción
    back/forum/game/bootstrap.php línea 5: if (true || (defined('GAME_DEBUG') && GAME_DEBUG)) anula el flag de debug. Cualquier notice/warning filtra rutas, SQL y estructura interna → HTTP 500 con stack en HTML/JSON.
  • P0 — Scripts de mantenimiento en URL pública
    public/clean_db.php (borra PJs mock), install_db.php, migrate_v2.php, mock_data.php, lint.php. Mitigación actual: cancp / staff en algunos; sigue siendo superficie de ataque si un admin es comprometido o hay bypass de sesión.
  • P1 — DDL en runtime desde plugin
    game_postcharacter_ensure_schema() ejecuta ALTER TABLE en hooks de post. Riesgo de bloqueo de tabla, condiciones de carrera en despliegues multi-request, y divergencia respecto a migrate_post_modifiers.php.
  • P1 — APIs de lectura sin autenticación
    Por diseño: get_active_pj_for_user.php, cards_for_post.php, busquedas_list.php, latest_activity.php. Aceptable para UX del foro; revisar rate limiting y campos expuestos (PII, staff flags).
  • P2 — SQL por concatenación sin prepared statements
    Patrón general $db->query("... {$uid} ...") con casts (int). Seguro si se mantiene disciplina; frágil ante refactors. Strings usan escape_string de forma irregular.
  • P2 — Inconsistencia de envelope de error
    Estándar: { ok, data, error: { code, message }, meta }. Excepciones: busquedas_action.php devuelve error como string plano. Rompe clientes genéricos y observabilidad.

4.2 Controles que funcionan bien

  • GameAjax::requireCsrf — Integración correcta con verify_post_check y header X-Mybb-Post-Key.
  • Ownership en mutaciones sensibles — Ej. purchase_attribute.php: valida user_id y estado aprobada del PJ.
  • Staff por personaje activo — staff_level en game_personajes, no solo grupo MyBB; coherente con controles .rpg-modonly en front.
  • Post-character linkage — Sin fallback a PJ activo cuando falta post_id/thread_id histórico (evita suplantación visual en posts antiguos).
  • IDs numéricos casteados — Convención extendida en endpoints revisados.

10. Plan de mejora — roadmap 8 fases · estimación 6–10 semanas

  1. Fase 0 — Hotfix producción (1–2 días): Corregir if (true) en bootstrap; revisar php.ini; bloquear URLs de clean_db, install_db, migrate_v2, mock_data en servidor.
  2. Fase 1 — Seguridad y consistencia API (1 semana): Unificar respuestas JSON en todos los ajax; auditar POST sin CSRF; revisar campos expuestos en GET públicos; rate limit básico en nginx para /game/ajax/.
  3. Fase 2 — Esquema y migraciones (1–2 semanas): Tabla game_migrations + runner idempotente; eliminar ALTER del plugin (solo migrate); documentar estado esquema por entorno.
  4. Fase 3 — Contratos (1–2 semanas): Completar OpenAPI de busquedas, cartas, announcements, progression; CI audit_backend_contracts.py; ejemplos para cada path nuevo.
  5. Fase 4 — Capa aplicación (2 semanas): Repositories por agregado; reducir ajax a orquestación; tests de integración en Services críticos (save PJ, cards_play, notifications).
  6. Fase 5 — Endpoints legacy (3–5 días): Implementar economía/inventario/tiradas en local o eliminar rutas 501 y páginas placeholder; actualizar OpenAPI.
  7. Fase 6 — Documentación (2–3 días): Reescribir docs/arquitectura/* al modelo D001; runbook backend-deploy.md; alinear README de game/.
  8. Fase 7 — Observabilidad (1 semana): Log estructurado en mutadores (uid, endpoint, pj_id); métricas error rate ajax; alertas 5xx.
  9. Fase 8 — Decisión rpg_bridge (opcional): Si se necesita backend externo: implementar plugin con HMAC según contrato envelope; si no, archivar docs de webhooks y rotación de tokens.

11. Fortalezas a conservar

  • Decisión D001 (datos locales) — Latencia baja, sin dependencia de red para mecánicas; adecuado para foro RP.
  • GameAjax + game_api.js — Patrón CSRF y envelope JSON claro; base sólida para escalar API.
  • Plugin game_postcharacter — Hooks bien elegidos; conteo por personaje (postnum/threadnum) alineado con identidad RPG.
  • Staff por PJ activo — Modelo de permisos más fino que solo grupo MyBB; coherente front/back.
  • AGENTS.md como fuente de verdad — Convenciones de entrypoints, plantillas y post-character linkage bien especificadas.
  • Services extraídos — CharacterSave, Progression, Notifications demuestran dirección correcta sin sobre-ingeniería prematura.
  • packages/contracts iniciado — Aunque incompleto, el estándar existe; solo falta disciplina CI.
